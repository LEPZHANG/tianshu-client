# Agent Note：设置面板继承了侧边栏的反色文字

Status: implemented

[English](2026-08-21-settings-panel-portal.md) | 中文

## 问题

在桌面客户端中打开 设置，面板无法阅读。文字确实存在且位置正确，但在面板的白色表面上不可见。

成因是[天枢侧边栏](2026-08-18-tianshu-desktop-integration.md)。该列绘制饱和蓝色，因此为自身子树重新绑定了中性文字色标记——品牌底色上的浅色文字，即已记录的局部重绑定范式。`SettingsRoot` 把触发按钮安置在 `sidebar.settings`，位于该列底部，并把模态面板渲染为该触发按钮的同级节点。于是面板落在被重新着色的子树内，把 `--dsw-alias-label-primary: rgba(255,255,255,0.95)` 继承到了自己的 `background: rgb(255,255,255)` 之上。

侧边栏的重新绑定是正确的。缺陷在于模态框根本不该就地渲染。

## 决策

`SettingsPanel` 改为 portal 到 `document.body`，与 `Modal` 和 `OnboardingSurface` 一致——那是 `ui-primitives` 中现有的两个全视口浮层，两者早已出于层叠上下文的理由使用 portal。本面板是最后一个就地渲染的浮层。

采用 portal 而非在浮层上把标记重新绑定回去，是因为被继承的值在面板内部无从得知。任何承载它的列都可能重设自身子树的样式；一个归属于视口的模态框，不应依据恰好承载其触发按钮的元素来解析颜色。重绑定标记的方案先被尝试并否决：`.root` 同时直接设置了 `color`，因此即便恢复标记，面板仍会经由 `color` 属性继承到白色。

`react-dom` 移入 `peerDependencies` 与 `react` 并列，遵循 `ui-trajectory` 的先例——该包的 React 是 peer，其渲染器也必须是。

## 备选方案

**在浮层上重新绑定文字色标记。** 最先尝试，在运行中的客户端上实测后依据证据否决：`.root` 除重绑定标记外还直接设置了 `color`，因此在浮层上恢复 `--dsw-alias-*` 之后，面板仍会经由 `color` 继承到白色。连 `color` 一并强制覆盖确实可行，但那会让每个浮层都背上一份针对任意祖先的防御。

**让侧边栏不为设置座位重新绑定文字色。** 只能修好这一个面板，且与该列自身的需求相冲突——触发按钮确实需要在品牌蓝上显示浅色文字。

**给面板显式指定 `color` 与背景色对。** 比 portal 更窄，且渲染结果正确，但它只覆盖有人想到要钉住的那些属性。字体、边框与滚动条标记仍会从承载触发按钮的任意元素继承。

## 权衡结果

侧边栏没有任何改变：设置 触发按钮仍然渲染为蓝底浅色，因为该按钮确实位于那一列中。

组件测试不受影响：它们通过文档级作用域的 `screen.*` 查询，portal 后的内容解析结果完全相同。若测试改为经由 `view.container` 断言，则会失效。

`prefers-reduced-motion`、焦点管理与 Escape 监听器均未改变——该监听器本就是文档级的。

## 测试

一个回归测试断言对话框不在渲染容器内部。已确认它在撤销 portal 时失败（`expected true to be false`），在应用后通过，因此它钉住的是「逃逸」这一行为而非实现机制。

并非仅凭静态检查，而是经 CDP 在运行中的桌面客户端上验证：修复前导航标签计算为白色面板上的 `rgba(255,255,255,0.95)`，修复后为 `rgb(15,17,21)`。随后对全部五个分区扫描了浅色叠浅色的文字。Agent 预设 中仍有一处命中——`当前使用` 徽标的白色文字位于其自身的深色药丸底 (`rgb(15,17,21)`) 之上，属于预期效果。

包测试全部通过（45 个），per-file 100%。`typecheck`、`lint`、`knip`、`constraints` 与 `verify-package-invariants` 均干净。`publint` 与 `rescope-vendor` 在暂存本次改动后失败情形完全相同，因此二者均为既有问题。
