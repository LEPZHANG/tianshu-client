# Agent Note: Real WebUI authentication replaces the placeholder login

Status: implemented

[English](2026-08-18-webui-auth-adoption.md) | 中文

## 问题

[占位登录界面](../feature/2026-08-18-gajz-login-surface.md)交付了一扇前门与一套客户端状态机，并且把话说明白了：它不授予任何东西，`curl` 可以完全绕过，它自己的 Known Limitations 也列出了真实实现将会撞上的三个障碍。之所以那样做，是因为 dsh 没有认证，而把认证做砸比不做更糟。

这个推理的前提是：替代方案只能是从零写宿主侧层。事实并非如此。`dsh-webui-auth` 就在 npm 上（v0.3.0，六个版本，MIT，零依赖），而它恰恰就是缺失的那一块——这使得继续交付一个什么都保护不了的界面不再站得住脚。

同时，本部署正从纯浏览器产品转向桌面客户端，而桌面用户读不到宿主日志。无论由什么来做认证，它的首启密钥都必须出现在人看得见的地方。

## 决策

删除占位包，挂载 `dsh-webui-auth` 作为产品的认证。

**它拦住了占位实现拦不住的东西。** 该插件在运行时包装 `webServer` 路由——不修改任何 dsh 源码，因此 dsh 升级不会让它无声失效——并覆盖四个面：SPA（302 到登录页）、`/plugins` 客户端插件包（302）、`/api`（401）、两条 WebSocket 升级（拒绝）。这些正是占位实现的 Known Limitations 中点名未受保护的那些面。其背后是：scrypt 密码哈希、HttpOnly 会话 cookie、跨重启持久化的会话、每 IP 限流，以及只有操作者能读到的每次启动随机 setup token。

这是**实测**而非读 README 得出的结论——四个面在无认证时全部拒绝，带上会话 cookie 后同样的请求全部成功。

**插件从本地 clone 消费，而不是从 npm。** `dsh-webui-auth/` 就在本检出旁边，web bundle 以 `link:` 依赖它——这正是该插件 README 中写明的「维护者开发模式」。该 clone 与已发布的 0.3.0 **字节一致**（diff 验证过，仅行尾符不同），因此这是换来源，不是换版本。

如此一来，天枢登录页就是一次普通的源码编辑：品牌蓝、左卡片右盾徽主视觉的两列舞台、标题「欢迎回来」。该页面本就在读 `--dsw-alias-*` 主题 token 并尊重浅/深色偏好，因此这是换皮，不是重做。

从 clone 工作还消除了 npm 路线的一个隐患。在 `link:` 安装下，插件把数据保存在自己的目录里、而不是回落到 `$DSH_HOME`——而那个目录如今是一棵 git 工作树。该 clone 的 `.gitignore` 覆盖了凭据文件与审计日志，但**没有**覆盖 `sessions.jsonl`（活动会话令牌）、`setup-token` 与 `audit-hmac-key`，三者均以 `0600` 写入。本次改动补上了它们，使该项目中的 `git add -A` 不会提交活动密钥。

**桌面壳负责把 setup token 呈现出来。** 它从子进程 stdout 抓取该令牌，并用带复制按钮的对话框展示——因为对桌面用户而言，那条日志并不存在。

## 设计稿要求但后端做不到的部分

参考设计稿有手机号字段与「验证码登录」标签页。`dsh-webui-auth` 认证的是用户名与密码，它完全没有手机号或验证码的概念。因此补丁后的页面询问的是「账号」，也没有第二个标签页。

「照样把标签页画出来」被否决了：一个点不动的控件比没有这个控件更糟，而占位实现自己的验证码路径——客户端完整、后端为零——正是本次改动要纠正的错误。

## 备选方案

**保留占位页，在它背后再加 dsh-webui-auth。** 否决：连续两个登录界面，其中一个是演戏。用户要为一次真实校验登录两遍。

**保留占位页以完全贴合设计稿，不做真实认证。** 该界面与参考稿高度吻合，且花了 28 个测试才建成。否决原因：贴合一张图并不是登录功能存在的意义，而且本部署正走向桌面客户端，未必永远待在回环地址上。

**在本仓库里自己写宿主侧层，而不是采用现成的。** 接缝确实好找，上一篇笔记也已经把它们标了出来。以那篇笔记自己的理由否决——token 的签发、存储、轮换，`unauthorized` 错误码，以及连接重试路径，都是实打实的产品面——区别在于：现在已经存在一份经过审阅的、恰好实现了这些的代码，再造一个买不到任何东西。

**fork 该插件而不是打补丁。** fork 能对登录页有完全的自由度，代价是要自己扛下安全相关代码（scrypt 参数、会话持久化、限流），并手工回合上游修复。否决：本次定制是表现层加一处路径解析，补丁恰好能精确表达它，且补丁在升级时会报错，而不是无声偏离。

**把数据目录问题提给上游，而不是打补丁。** 这是正确的长期做法，补丁并不能取代它。此处先以补丁处理，是因为它避免的故障——下次 install 就丢掉管理员账号——是立刻会发生的。

## 权衡结果

产品现在有了真正拦得住的认证，`--host 0.0.0.0` 也从「自动否决」变成了一个可以真正讨论的问题。CLI 中的那道拒绝依然保留，本次改动并未解除它：SPA、`/plugins`、boot manifest 与 HMR 端点都已加门，但对外暴露到网络仍需就 TLS、origin 策略与信任围栏单独评审。

代价是：一条安全关键路径依赖了本仓库之外的包，锁在一个固定版本上并带本地补丁。升级时必须**重新实测那四个面**，而不只是确认补丁还能打上。

登录页在两处可见地不再匹配设计稿——没有手机号字段、没有验证码标签页——因为后端两者皆无。这一点如上文所记，而不是被粉饰过去。

占位包、它的 28 个测试与客户端 `AuthClient` 接缝均已删除。那套接缝的形状并没有白费：它本就是照真实后端设计的，而取代它的正是一个真实后端。

## 测试

门禁本身没有自动化覆盖：插件是外部依赖，测试是它自己的，而本仓库没有「启动服务并探测」的测试通道。四个面是对着真实运行的 `dsh web` 实测的——先无认证、再带会话 cookie——浏览器流程也端到端跑通（重定向到登录页、登录、进入应用）。插件升级时请重跑这些探测：**补丁能干净打上，不等于门禁仍然成立**。
