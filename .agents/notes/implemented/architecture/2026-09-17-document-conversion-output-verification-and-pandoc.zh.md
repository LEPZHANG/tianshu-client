# Agent Note: 一次转换究竟产出了什么，又付出了什么代价

Status: implemented

[English](2026-09-17-document-conversion-output-verification-and-pandoc.md) | 中文

## 问题

转换 seam 已经交付并且能用，但产出的结果很差，而差在 harness 看不见的地方。

用户的抱怨是 `convert_document`「效果很差」。复现之后，这一句抱怨分解成四种互不相同的失败，原设计一种都检测不出来：

1. **转换器对一个根本不是文档的文件也报告成功。** seam 当时只检查承诺的那个文件是否存在。LibreOffice 会退出 0 并写出文件：一份没有渲染出任何页面的 PDF 导出、一份没有幻灯片文本的 HTML 演示文稿导出、一个内里其实是 Writer 文档的 `.odp`。这些全都通过了存在性检查，并作为成功的转换抵达模型。
2. **损坏的源文件失败时，诊断信息什么也没指出。** 有些工具写 `.docx` 时跳过了 ZIP 校验和，条目里明明带着数据，声明的 CRC 却是零。Word 能打开它；LibreOffice 拒绝它，并且只说转换失败了。拿到这条消息的模型会重试转换，因为消息里没有任何内容表明问题出在输入上。
3. **PDF 抽取为空，是两个相反的问题共用一种症状。** 无论是扫描件（本来就没有任何文本），还是 `pdftotext` 解码不了其文本的 PDF，它都会退出 0 并写出一个空文件。前者需要 OCR，后者需要换一个工具；过去的失败信息两者都没说。
4. **`lossy` 只说丢了东西，从不说丢了什么。** 被告知一条路由是 lossy 的模型只能含糊其辞。它没法告诉用户：电子表格导出只保住了一个工作表，或者文本文件里的表格现在是用空格对齐的。

还有一个结构性问题：LibreOffice 的 HTML 导出给出的是 Writer 排版引擎所看到的东西——一串扁平的、绝对定位的 `<p>` 元素，没有标题、没有列表、没有表格。它是一页版面的忠实图像，却是一份无用的文档，而当时它是 harness 仅有的 HTML 路由。

## 调研

用户指出了一个第三方转换器，作为做法上的参考。它的技术手段经阅读后在本仓库中重新实现，其代码一行未抄——它采用 Non-Commercial License，并打包了一个 AGPL-3.0 依赖，因此它可以启发设计，不能进入本仓库。

那个项目做了、而本项目当时没做的事：校验转换器产出的内容而不是它的退出状态、在把损坏的压缩包交出去之前先检出它、对扫描件 PDF 给出诊断而不是报告一个空结果，以及明确告诉调用方一次转换丢掉了什么。

它做了、而本次改动有意不做的事——理由是范围，不是优劣：基于 pdf.js 操作符列表的图像覆盖率分类、带双引擎交叉校验的表格候选打分，以及按格式重建编号。每一项都是相当大的子系统，缺了它们损失的是精度，不是正确性。

## 决策

### seam 校验字节，而不是退出码

`verifyConvertedBytes(format, bytes)` 读取转换结果，查找该格式据以被识别的标志：PDF 的 trailer、复合文件头、OOXML 中写明生成应用的部件、明确声明该格式的 ODF `mimetype` 条目、RTF 签名、HTML 页面中的可见文本、文本文件中的非空白字符。输出未通过检查的步骤报 `CONVERT_OUTPUT_UNUSABLE`，并写明缺的是什么。

这段逻辑放在 seam 而不是各个提供方里，因为它是目标格式的属性，不是某种机制的属性；也因为自己检查自己成果的提供方，可能在同一件事上错两次。提供方现在只返回 note，不做校验；校验由 seam 负责。

这项检查要读文件，因此设了上限：`maxVerifyBytes`，64 MiB，做成 Config 字段，因为它在内存开销与检出能力之间的权衡取决于每个部署自己的文档。比这更大的结果显然就是一份文档。

为此 seam 需要自带一个 ZIP 读取器——`isZipContainer`、`readZipEntries`、`readOdfMediaType`——大约九十行，读的是中央目录。读不了的容器会被报成不可读，而不是报成空压缩包，这样一来，被截断的文件或 ZIP64 文件就不会因为读不出任何条目而通过建立在其之上的每一项检查。

### 损坏的容器在转换器看到它之前就被指名

LibreOffice 提供方会先读一遍 ZIP 源文件，报出那些数据非空、CRC 却为零的条目：`CONVERT_SOURCE_DAMAGED`，列出前三个，再给一个总数。它之所以在这个时点做，是因为此刻它掌握的信息仍然多于 LibreOffice 的诊断将会给出的信息。这里同样设了上限，由 `MAX_PREFLIGHT_BYTES` 控制——它是模块常量而不是 Config，因为这道预检只是对一个反正也会拒绝该文件的转换器所做的优化，没有留给部署方决定的余地。

### 抽取为空时给出诊断，而不只是拒绝

结果已经为空时，poppler 提供方会去问一次 `pdffonts`。没有嵌入字体就意味着没有文本层：报 `CONVERT_SOURCE_SCANNED`，消息中说明这些页面必须先经 OCR 读取。有字体则意味着文本受保护，或者采用了无法映射的编码：报 `CONVERT_PROVIDER_FAILED` 并如实说明。`pdffonts` 给不出答案时，消息会把两种原因都写出来，而不是挑一种——诊断不可用只影响措辞，绝不影响转换本身。

### note 承载保真度承载不了的信息

一个步骤返回若干 `ConvertNote` 值——`{ code, message }`——转换结果把它们带上，并按 `code` 去重。`convert_document` 把它们列在 **What this conversion did not carry over:** 之下；只有当一条 lossy 路由什么也没报时，才退回到那句泛泛的 lossy 说明。

这些消息是写给转发它们的模型看的，不是写给日志的。「The CSV export keeps the first sheet's values and drops the other sheets and every formula」是模型可以直接交给用户的一句话；「lossy」不是。

### pandoc 作为保结构的转换器加入

`packages/convert/document-convert-pandoc` 注册十六条边：`{docx, odt, rtf, html}` 到 `{docx, odt, rtf, html, txt}`，去掉源与目标相同的那些。

两个转换器仅凭各自的声明就把格式分完了，两个包谁也不知道对方存在，因为规划器把保真度排在优先级之前：

- 以 HTML 为目标或以 HTML 为源的边是 `faithful`、优先级 20，因此 pandoc 从 LibreOffice 的 `faithful`、优先级 10 手里拿走了这些边。
- 办公格式互转的边是 `lossy`——pandoc 是按自己的文档模型重建文档，而不是在原文件格式内往返——因此无论优先级如何，这些边都留给 LibreOffice。它们仍然被声明出来，这样只装了 pandoc 的容器依然能按已声明的代价完成 `docx → odt`。

提供方不做假设，而是直接问装好的 pandoc 能做什么：先用 `--version` 要求主版本号至少为 3（这是 `--embed-resources` 所需的下限；低于它时，HTML 目标产出的是指向并不存在的图片文件的引用），再用 `--list-input-formats` 和 `--list-output-formats`，并把声明的路由过滤成这两条命令报告的范围。这样就不必靠版本号推算来回答本包不该回答的问题，比如某个构建是否带 RTF 读取器。答不上来的 pandoc 一律按不存在处理。

没有 `→ pdf`：那需要一个 LaTeX 引擎，体量比 pandoc 大一个数量级，应当是独立的提供方。也没有 `→ pptx`：pandoc 的演示文稿写出器会给每个标题凭空造一张幻灯片，那是造了一份新文档，不是转换。

该插件在 base bundle 中默认挂载，紧挨着 poppler，因为可执行文件不在时它会退化成什么也不注册——正是 poppler 已经依赖的那种优雅降级。

## 后果

- 产出的文件不是文档时，转换现在会失败，而此前会成功。这正是本次改动的目的；对任何此前默默接受这类结果的组合来说，这是一次行为变更。
- 五个 convert 包里有四个新增了对转换器输入或输出的限长读取。每个上限都由一项使用稀疏文件的测试来触发，因此 64 MiB 和 4 MiB 两个阈值不必真的写出这么大的文件就能覆盖。
- `convert_document` 的结果多出了路由报出的那些 note——几行短文字，其长度与步骤数成正比，而不是与文档大小成正比。
- 这五个包共有 274 项测试，逐文件覆盖率 100%。

## 曾考虑的替代方案

**信任转换器，什么都不检查。** 这就是当初交付的做法，也正是那句抱怨所指的东西。退出码只说明程序结束了。

**把校验放进每个提供方。** 不予采用：这项检查是目标格式的属性。在各提供方之间复制它会产生漂移，而自己校验自己成果的提供方，根本没有独立的检查。

**复用参考项目的分类流水线。** 因许可证否决——它的 Non-Commercial 条款和 AGPL-3.0 依赖与本仓库不兼容——也因范围否决。这些技术手段是依据其说明重新实现的，它的代码没有被读进这里的任何文件。

**把 pandoc 作为主要的办公格式转换器。** 不予采用：pandoc 按自己的文档模型重建 `.docx`，会丢掉 LibreOffice 保住的东西——后者是在该文件格式内做往返。每个转换器各自拿走与其机制相配的那些边。
