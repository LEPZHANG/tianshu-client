# Agent Note: 文档转换——以路由规划为核心的能力 seam

Status: implemented

[English](2026-09-15-document-conversion-capability-seam.md) | 中文

## 问题

harness 此前无法把文档从一种格式转换成另一种。被要求把 `.docx` 变成 PDF 的 agent（智能体）手上只有 `bash`，于是只能依赖碰巧已经安装的转换器，用模型猜出来的参数去调用，既拿不到结构化结果，也无从告知用户输出是否保真。

最朴素的做法——一个直接 shell 调用 LibreOffice 的工具——一碰上真实的转换程序就站不住。有三个事实让它失效，而这三个事实都是实际做转换测出来的，不是从文档里读来的：

1. **`soffice` 对自己做不到的转换也退出 0。** 让它把文本转成 `pptx`，它会写出一个 2 KB、没有任何幻灯片的演示文稿；让它把 Writer 文档转成 `odp`，它会写出一个顶着 `.odp` 文件名的 ODF *文本*文档；让它把 PDF 转成 `odt`，它会写出一个顶着 `.odt` 文件名的 ODF *图形*文档。信任退出码的包装层会报告成功，并把一个损坏的文件交回去。
2. **只写 `--convert-to <ext>` 会选错过滤器，或者根本选不到。** 对 HTML 源文件，`--convert-to docx` 会以「no export filter」失败；对同一份输入，写明 `docx:Office Open XML Text` 就能成功。正确的过滤器取决于文档是被哪个应用载入的：同样是 `html`，从 Writer 出来是 `HTML (StarWriter)`，从 Calc 出来是 `HTML (StarCalc)`。
3. **没有哪一个转换器能覆盖需求中的整张矩阵。** LibreOffice 无法让 PDF 成为可用的源格式：它的 Draw 导入只能导出一块由定位文本框拼成的画布。十三种格式两两互转，是任何单一程序都撑不起的承诺。

## 决策

转换是一条能力 seam——`ctx.documentConvert`：路由知识集中在一处，具体机制藏在各个提供方后面。

- `packages/convert/document-convert`——Service Definition：十三种格式的封闭词汇、提供方注册表、路由规划器和步骤执行。
- `packages/convert/document-convert-libreoffice`——LibreOffice 的 headless 模式，覆盖三大办公格式族，以及每个族到 PDF 的转换。
- `packages/convert/document-convert-poppler`——`pdftotext` 与 `pdftohtml`，注册为两个提供方，因此缺少其中第二个可执行文件时只损失它自己那条路由。
- `packages/convert/tool-document-convert`——面向模型的 `convert_document` 工具。

### 提供方声明路由，seam 在其上做规划

提供方声明静态的 `ConvertRoute` 边——`from`、`to`、`fidelity`、`priority`——以及一个开销很小的同步 `available()`。seam 用所有可用提供方的边构建一张图并在图上搜索。选择过程是确定的，且与注册顺序无关：排序依据依次是步骤数最少、最差一步的保真度最高、最弱一步的优先级最高；候选路径按 seam 自己声明格式的顺序枚举。

**多步计划是目的本身，不是一项优化。** 大多数跨族转换只有靠它才存在：`pdf → txt → xlsx` 能从一份 PDF 抵达电子表格，而把结果报成 `lossy` 恰好说清了发生过什么。默认上限是两步——第一跳覆盖单个转换器能做的事，第二跳借助一种中间格式抵达目标，第三跳买来的只是无人能为其担保的转换链。

这也是 poppler 与 LibreOffice 同期交付、而不是延后交付的原因。没有文本抽取，PDF 作为源格式就是一条死路，矩阵上会留下一个再怎么规划也补不上的洞。

### 保真度按边声明，并按整个计划中最差的一步上报

`faithful` 表示结构和格式都带得过去；`lossy` 表示内容带得过去、版式带不过去。它属于一条边，而不属于某个提供方：LibreOffice 在 `docx → odt` 上是 faithful，在 `docx → txt` 上是 lossy。一个计划上报其各步骤中最差的那个判定，工具再在结果里用文字把它说明白——因为模型把转换后的文件交给用户时，需要知道版式没有保住。

### 路由表是实测得出的，缺项是有意为之

每一条表项都经过验证：在每种源格式的 fixture（测试前置数据）中放入一个唯一 token，执行转换，再按目标格式使用的每种编码在输出中查找该 token。问题描述中列出的那四种转换正是因此缺席；`ppt`/`pptx → html` 也缺席，因为 XHTML 导出会丢掉从这两种格式导入的幻灯片文本，却能保留原生 `odp` 的文本——所以它们改为经 `odp` 两步抵达 HTML，而不是走一条只对一种源格式有效、对其余源格式悄悄失败的边。

单元测试断言的正是这些*缺项*，因此谁若认为某条路由本该存在而想把它加回来，就必须重新验证它。

### 只在调用方能采取行动的地方抛出歧义

获胜计划用到的某条边上，提供方之间出现无法打破的并列时，seam 报 `CONVERT_ROUTE_AMBIGUOUS`，消息中写明用于钉住选择的 `routes` 配置。未被用到的边上的并列则忽略——那不是这个调用方的问题。两条完整*路径*之间的并列不报错，而是由确定的枚举顺序决出胜负：没有任何配置旋钮能让调用方裁决它，而大声失败只会平白挡住工作。

### seam 不是隔离边界

提供方把 argv 交给 `ctx.subprocess`，因此转换器是以 harness 进程自身的权限在写文件。隔离决策由 `convert_document` 工具在派发之前作出：它通过 `ctx.fs` 解析输入和输出两条路径，在 `read-only` 下拒绝每一次调用，在 `workspace-write` 下要求输出落在工作区根目录内。在进程内直接调用 `ctx.documentConvert` 的调用方会绕过这道决策，两份 README 都把这一点写明了。按 `dsh-bash-sandbox` 那套做法实现沙箱化提供方属于延后事项，而不是假装已经做到。

## 曾考虑的替代方案

**一个直接 shell 调用 LibreOffice 的工具。** 被上面三个事实否决：它会把损坏的输出报成成功，而且根本无法表达「PDF 作为源格式」。

**纯 JavaScript 库（mammoth、xlsx、pdf-lib）。** 不需要外部依赖，但它们覆盖不了整张矩阵，在真实文档上的保真度也很差。它们同样不会暴露输出类型错误这个问题，因为每个库只写一种格式。

**远程 HTTP 转换服务（Gotenberg 之类）。** 它日后完全可以作为一个提供方加进来——seam 的存在正是为了让这成为可能——但把它当作唯一后端，会让转换必须依赖网络和一套部署，而且会为了本机就能完成的工作把文档送出进程之外。

**不设步数上限的通用最短路径搜索。** 不予采用：无上限的链条会产出一些路由，而它们的保真度声明无人能辩护。两步是能补上跨族缺口的最小上限。

**按提供方而不是按路由声明保真度。** 更简单，但是错的：它会逼着 LibreOffice 对 `docx → odt` 和 `docx → txt` 给出同一个判定，而诚实的选法只能是全部标成 `lossy`，那等于什么也没告诉模型。

**对路径并列也抛出 `CONVERT_ROUTE_AMBIGUOUS`，而不只是对提供方并列。** 不予采用：配置钉住的是每条边上的提供方，不是路径，因此这个错误说不出任何补救办法。

**每次调用都采样提供方可用性。** 不予采用：seam 要求 `available()` 开销小且同步，而 spawn 一个进程做不到这两点。可用性只在插件 apply 时采样一次；代价是此后才安装的转换器要等到重新挂载才可见，两份提供方 README 都记录了这一点。

## 后果

这张矩阵对自己是诚实的。已注册转换器做不到的转换会以 `CONVERT_ROUTE_UNSUPPORTED` 失败，并在消息中写出两种格式和步数上限，而不是产出一个打开后空无一物的文件。走 lossy 路由时，面向模型的结果里会如实写明。宿主机上没有 LibreOffice 的组合会退化到仅有的那些转换器，而不是启动失败。

代价有两项：一是用户可能只把它描述成一项功能，实现上却是一个五种角色的包族；二是这张路由表只是某一代 LibreOffice 的快照——未来版本里的一次过滤器改名会表现为转换失败，而构建过程中没有任何环节能发现它。重新验证是一套写在文档里的手工流程，不是门禁。

冷启动是一次转换的主要开销：第一次运行 `soffice` 要付出数秒的启动时间，而两步计划每一步都要付一次，因为每一步都是独立进程。常驻的 LibreOffice 监听进程可以把这笔开销摊薄，此事已延后；它会重新引入共享用户配置目录的争用，而每次转换各自私有的用户配置目录正是为了避免这种争用而存在。

## 测试

路由规划器、格式词汇和工具的各项守卫都有单元测试，覆盖率门禁要求这个包族里每个文件都达到 100%。提供方的 argv、过滤器选择、输出发现和失败分类都跑在一个脚本化的 `ctx.subprocess` 后端上，因此没装转换器的机器同样会执行真实的提供方代码。一组带跳过守卫的用例会运行真实的 `soffice` 和真实的 poppler，断言源文件的内容确实到达了输出，而不只是断言生成了一个文件。`convert-document` 的 ACP（Agent Client Protocol）快照钉住工具 schema、提示词分节和 transcript（文本记录）：其中 seam 和规划器都是真的，只替换掉外部转换器——真实 LibreOffice 生成的 PDF 内嵌时间戳且随版本变化，它的字节大小钉不住。
