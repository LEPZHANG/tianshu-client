# Agent Note: 自定义提供方卡片上的本地模型接入预设

Status: implemented

[English](2026-08-27-tianshu-local-model-presets.md) | 中文

## 问题

产品正在扩展到互联网 API-key 提供方之外：所有者会在本地 GPU 上部署模型，局域网可达的 GPU 服务器也在范围内。harness 的模型层已经同时服务这两者——`llm-pi-ai` 说 OpenAI 兼容协议，而设置里的 Models 页面已经有一张手工声明提供方的卡片（`CustomProviderCard`），它接受任意 base URL，并在 `{baseURL}/models` 发现模型。

缺的是知识，不是能力：一个在本地部署 Ollama、vLLM 或 llama.cpp 的用户，必须知道自己那套运行时的惯用端口，还要手工填出一份五个字段的声明。在产品如今想要推广的路径上，这就是摩擦。

## 决策

自定义提供方卡片以三个一键预设 chip 开头——Ollama（`http://127.0.0.1:11434/v1`）、vLLM（`http://127.0.0.1:8000/v1`）、llama.cpp（`http://127.0.0.1:8080/v1`）。点击是一次**填写动作，既不是状态，也不是提交**：它设置路由 id、显示名和 base URL；原本就必需的一切（至少一个模型、可选的密钥）照旧门控创建按钮。路由词干已被占用的 chip 会自行禁用，而不是替用户造一个他并没有选择的带后缀 id——占用规则随后由既有的字段级提示点名冲突。

局域网 GPU 不需要专门的入口：同一张卡片，把服务器地址粘贴为 base URL，就是被文档化的流程，README 现在也写明了这一点。

本次改动不附带任何模型层或 settings schema 的改动。预设完全位于客户端卡片内（`LOCAL_PRESETS` 常量）；它们产出的提供方 profile 与手工填写的声明逐字节相同，因此适配器、凭据和发现路径永远不会知道曾经有过预设。

## 后果

拥有本地运行时的用户点一下 chip、至多改个端口、拉取模型，然后创建提供方。局域网 GPU 用户粘贴 `http://<host>:<port>/v1`，走完全相同的流程。

预设列表刻意只有三项，不是一个可扩展面：这些端口是那几套运行时默认安装时的惯例，而不遵守自身惯例的运行时仍由手工录入来服务。日后新增一个预设，只是一个常量加两个 locale 键。

面向密码认证的远程 GPU 的 SSH 隧道能力**有意不**包含在本次改动里：它是一个宿主侧插件（隧道生命周期、一次性密钥下发、凭据存储），另行设计。本 Agent Note 只覆盖零基础设施的那些路径。

## 曾考虑的替代方案

**专门做一种「本地提供方」卡片类型。** 不采用：这会为仅仅是字段取值上的差异而分叉声明面。现有卡片已经校验了一份本地声明所需的一切；第二张卡片只会与第一张渐行渐远。

**自动探测正在运行的本地运行时。** 不采用：在卡片打开时探测端口，等于在一个设置表单里做有副作用的网络扫描；而且当运行时还没跑起来（用户提前配置时的常见情形），结果会报「未找到」，读起来像是出错。

**在点击 chip 时探测。** 同理不采用：点击必须保持为纯填写，而既有的「获取可用模型」按钮已经按需探测端点，并给出真实的错误报告。

## 测试

`provider-form.client.spec.tsx` 新增了一个 `local runtime presets` 块：一个用例驱动 vLLM chip，断言路由、显示名与 base URL 三个字段已被填入（且没有提交任何东西）；另一个用例断言被占用的词干恰好只禁用那一个 chip，相邻的 chip 仍然可用。包内套件 231 项测试通过；`typecheck` 干净；客户端 bundle 已重建（`lib/client.js` 服务于正在运行的 web 应用）。
