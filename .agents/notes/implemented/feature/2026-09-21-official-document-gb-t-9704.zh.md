# Agent Note: 按 GB/T 9704—2012 生成公文——转换 seam 的第二个消费方

Status: implemented

[English](2026-09-21-official-document-gb-t-9704.md) | 中文

## 问题

产品此前已经能教模型写出公文的文字——文种、标题三要素、层次序数、公文语体——但只有版面对了，公文才算公文。GB/T 9704—2012《党政机关公文格式》规定：A4 纸，156 × 225 mm 版心，天头 37 mm、订口 28 mm，每面 22 行、每行 28 字，正文三号仿宋、标题二号小标宋，发文字号下 4 mm 处一条红色分隔线，版记的分隔线分别为 0.35 mm 和 0.25 mm。提示词无法让一个文件真的具备这些。被要求写一份通知的模型，产出的文字语体正确，文档却一量尺寸就通不过检查。

所以办公套件需要的是一个工具，而不是第六段提示词。悬而未决的问题是：既然 harness 已经有一条主题就是文档格式的 seam，那么一个*写出*某种格式的工具应该归在哪里。

## 决策

新增 `packages/convert/tool-official-document`，注册面向模型的 `write_official_document` 工具，并让它成为 `ctx.documentConvert` 的**第二个消费方**，而不是另开一条 seam。这样的分工正好对应两边各自能决定的事：模型挑选文种，按「发文机关+事由+文种」写出标题，指明主送机关，并划分正文；工具负责设定版面，并拒绝标准不允许的文档，一次把违反的条款全部列出，好让一次重试就能全部改完。

**不新增第十四种 `DocumentFormat`。** `DocumentFormat` 是十三个 id 构成的封闭联合类型，而 `odt` 本来就在其中。工具用 `fflate` 自行拼装 OpenDocument 文本文件（`mimetype` 放在最前且以 STORED 存储，mtime 固定为 1980-01-01，因此在任何机器上产出的字节都一致），其余格式则沿 LibreOffice 已经声明的边抵达——`odt → docx`、`odt → pdf`。加入 `fodt` 就要为了给一种文件起名而拓宽一个封闭联合类型，且 seam 此后还必须支持从该格式出发的路由，却换不来既有 `odt` 边尚未给出的任何东西。这正是 seam 当初为之而建的格局：一种既有格式的新产出方，免费获得其余所有格式。

**沙箱护栏成为 `dsh-tool-document-convert` 的公开导出。** seam 明确不是隔离边界——它的提供方把 argv 交给 `ctx.subprocess`，以 harness 进程自身的权限写文件——因此每个消费它的工具都要在派发之前自行决定隔离。两个工具作出的决定完全相同，于是 `sessionCwd`／`filePolicy`／`assertWritable`／`assertWithinWorkspace` 有了唯一的归属地，两个断言函数则接受一个操作名参数。同样的理由后来也覆盖了两者作为「写单个文件的 convert 家族工具」所共有的其余事实：工具调用预算检查、展示元信息的类型收窄，以及 `notes` 输出 schema。代价是一个工具包依赖另一个工具包；另一种做法是把护栏移进 seam 所在的包，那会与该包自己的 README 相抵触。

**默认输出为 `.docx`。** 这是用户在推荐的 `.odt` 之外作出的选择。它让默认路径硬依赖 LibreOffice：宿主机若没有 `soffice`，就会以 `OFFICIAL_DOC_FORMAT_UNREACHABLE` 失败，该错误会指出 `format: "odt"` 是那个不需要转换器的选项。这一点记在 README 的 Known Limitations 一节里，而不是藏在一次静默回退背后。

## 曾考虑的替代方案

**再加第六个纯提示词 skill（技能）。** 直接否决：这正是不奏效的那条路。提示词可以说三号仿宋，文件却依然不会真的是三号仿宋。

**直接生成 `.docx`，而不是先生成 `.odt`。** 不予采用：走 OOXML 等于把同一份标准的版面再实现一遍，而 seam 的存在恰恰是为了让一个产出方抵达多种格式。ODF 还为每种文字分别保存字体属性，这正是 CJK 版面所需要的——`style:font-size-asian` 和 `style:font-name-asian` 与那对 `fo:` 属性并列。（实现过程中漏掉 `-asian` 那一半曾是一个真实缺陷，现已有回归测试看守。）

**一次只收集一处违规。** 不予采用：遇到第一个问题就抛错的校验器，每个出错字段都要花掉模型一次往返。校验在写出任何文件之前先跑完，并把所有条款一起报出来。

**用 `fc-match` 探测宿主机上的字体。** 延后：跨平台不可靠，而且答案不会改变文件里的内容。工具写入的就是标准点名的那几种字体，并报告缺少这些字体的机器是否会改用其他字体。

**为 ACP（Agent Client Protocol）快照准备一个 fixture（测试前置数据）转换器，** 就像 `convert-document` 需要的那样。没有必要：那个场景钉的是真实 LibreOffice 生成的 PDF，其字节里带着时间戳。本场景写的是 `odt`，由工具确定性地构建，因此不挂载任何提供方，transcript（文本记录）也能逐字节一致地回放。

## 后果

标准要求的两件事确实做不到，README 中如实说明，而不是拿近似做法糊弄过去：

- **印章（§ 7.3.5.1、§ 7.3.5.3）。** 印章是一张红色印模图像。工具实现的是 § 7.3.5.2，即不加盖印章的形式，并且从不作相反声称。
- **字体。** 文件写入的就是标准点名的那几种字体，而缺少它们的机器会改用其他字体：每一处尺寸、缩进和线条都按标准设定，字形则不是。这里记下的那句「没有哪种格式能把机器上缺失的字体嵌进去」是错的：在部署提供字体的场合，[内嵌字体](2026-09-24-official-document-embedded-fonts.md)会把字体文件带进公文内部，并在结果 note 里说明哪些字体随行。

第 10 章的三种特定格式（信函、命令（令）、纪要）尚未实现；版记是随文排下来的，没有钉在页脚。

版面代码拆成了 `odf.ts`（页面几何与样式）和 `content.ts`（各类元素），这与已批准方案中单一 `src/odf.ts` 的安排不同——两者没有共享状态，而逐文件 100 % 的覆盖率门禁在拆分后读起来更清楚。

套件改称办公六件套（`id` 仍为 `office-essentials`，因此安装状态不受影响），新的 skill 教模型用好该工具但不设门槛：无论套件是否安装，`write_official_document` 都由 base bundle 注册。四处依赖的 fixture 和断言随这次改名一同调整。模型可见文本是工具的 schema、它的那一节提示词，以及安装好的 SKILL.md；无密钥的 ACP 场景 `official-document` 钉住一次被拒绝的调用及其改正后的重试，因为指名条款的拒绝行为正是这套校验设计存在的意义。
