# Agent Note: a 公文 heading splits on any mark that closes one, a collection supplies one face, and a converted .docx drops the fonts it repeats

Status: implemented

[English](2026-09-28-official-document-heading-split-collections-and-repeat-fonts.md) | 中文

本篇放宽了[公文层次字体](2026-09-28-official-document-level-faces-and-dev-fonts.md)所交付的一条规则，并在两处扩展了[把公文字体装进文档](2026-09-24-official-document-embedded-fonts.md)。两篇的其余决定都仍然成立。

## 问题

一位用户在天枢桌面客户端里报告了 `write_official_document` 产出文件的若干缺陷，每一处都追溯到一条曾被记为「可以接受」的假设。

**以冒号收尾的标题让整段都套上了层次字体。** 模型写的是 `三、压实工作责任：各地区各部门要确保见效。`——标题以「：」收尾，正文接在后面。切分只认「。」，而全段唯一的「。」正好是最后一个字符，于是整段被排成 `BodyLevel1`：标题和正文都是黑体。这条规则本是刻意留下的限制，当初还连同它所否决的备选一起记录在案；模型最平常的写法正是那个备选所预见的，而限制恰恰在它身上触发。

**即使部署方提供了黑体与宋体，它们也带不进文件。** 标准点名的五款字体中桌面端只携带三款，而缺的这两款正是 Linux 或 macOS 阅读方会被替换掉的。光提供宋体也补不上：Windows 上的 SimSun 以 `simsun.ttc` 分发，而读取器只认 `.ttf`，并在版本标签处拒绝 `ttcf` 文件，于是这个字族被静默跳过。

**一页公文转出来 15.1 MB。** `EmbedFonts` 让 LibreOffice 把文档用到的每个字面都写进 OOXML 导出，而一个没有独立粗体字面的中文字族会同时写进 `w:embedRegular` 与 `w:embedBold` 两个槽。这两份部件承载的是同一款字体，但字节并不相同：OOXML 会用该槽自己的 `w:fontKey` 混淆每个部件的前 32 字节，而每个槽各有自己的 key。文档里一半的字节就是这三款字体又存了一遍。

**一份在其他阅读器里都正确的文件，在 WPS 里字体是错的。** 五款字体都提供之后，这份 `.docx` 在结构上无可指摘：五个字族都已声明、五份有效的单字体面都已嵌入、每个段落都解析到 § 7.3.3 与 § 5.2.2 要求的字面，而 LibreOffice——读的就是文档自带的嵌入部件——渲染时一个替身都没用。可桌面端 `.docx` 的默认处理程序 WPS 依然把黑体、宋体、仿宋_GB2312、楷体_GB2312、方正小标宋简体全部替换了。文档里写的是它们的英文族名 `SimHei`、`SimSun`、`FangSong_GB2312`、`KaiTi_GB2312`、`FZXiaoBiaoSong-B05S`，而 WPS 是按文档写出的名字来解析字族的。把族名就地改写、字体部件一个字节都不动，同一份文档便渲染正确——缺陷就此被锁定在命名上。

## 决定

### 任何能收尾标题的标点都会收尾标题字体

`splitRunInHeading()` 取第一个 `。`、`！`、`？`、`；`、`：` 或换行。标点留在标题里，而换行只是分隔、不属于任何一侧。标点之后没有内容的段落是单独成行的标题，仍用 `BodyLevel1` 或 `BodyLevel2`；第三层、第四层整段仍是仿宋，依旧不切分。逗号刻意不作边界：`一、加强组织领导，压实工作责任。` 是一个标题，不是标题加一句话。

### 被点名的字族从集合里取出为单字体面

`loadEmbeddableFonts()` 读取 `.ttf` 与 `.ttc`。它遍历文件中的每一个 TrueType 字面，把各自声明的字族与 `metrics.ts` 写进样式的五个名字匹配。文件单独承载的字族就直接嵌入该文件；集合中的字族会被重建成单字体 sfnt——沿用该字面自己的头与表目录，把每条记录的表偏移改写为新布局中的位置，并复制它点到的表字节——因为写进文档的 `ttcf` 文件没有任何阅读器能解析。LibreOffice 已经演示过这一点：它把整个集合原样嵌入，产出的 `word/fonts/*.odttf` 头四个字节就是 `ttcf`。带 CFF 轮廓的字面（`OTTO`）仍然在 sfnt 版本处被拒绝，无论单独存在还是在集合里；每个字面的嵌入许可由它自己的 `fsType` 决定。

### 文档按标准的名字来称呼字体

`metrics.ts` 的 `FONT`——因而 `styles.xml` 写出的每个样式、导出携带的每个 `<w:rFonts>`——把五个字族命名为方正小标宋简体、仿宋_GB2312、黑体、楷体_GB2312、宋体。这既是标准自己的叫法，也是这些文件认的名字：一个中文字体会为 `zh-CN` 和 `en-US` 各声明一次同一字族，因此 `loadEmbeddableFonts()` 无论如何都拿同一份清单去匹配声明，目录扫描不受影响。`fontNote` 报告的也是文档真正写出的那些名字。

这一改动正是让嵌入字面在 WPS 里可达的原因；它同时也让「阅读器替换」不再被掩盖：在没装黑体的机器上，写着 `SimHei` 的文档会被 WPS 静默换成别的字体，而嵌进去的那份文件就躺在包里没人读。

### 非 ASCII 字族会得到转义后的包内部件名

`fontEntry()` 把 `[A-Za-z0-9._-]` 之外的字符转义成 `_u<码点>`，而不是替换成一个裸下划线。ZIP 条目名按字节比较，而裸下划线不是单射：仿宋_GB2312 与楷体_GB2312 会双双变成 `Fonts/___GB2312.ttf`，黑体与宋体则双双变成 `Fonts/__.ttf`——一款字体会覆盖另一款，某个字面就会被以另一个字族的名义嵌入。转义后每个条目仍是 ASCII 且互不重复，而本来就是 ASCII 的字族保持原有条目名不变。

### 转换出的 .docx 会丢掉重复的字体

`dedupeEmbeddedFonts()` 逐个 `<w:font>` 遍历字体表，在每个字族内保留首次出现的字体，移除其后的槽、它们的关系，以及不再被任何留存关系点名的部件。两个槽指向同一部件，就显然是同一款字体；否则透过各自的 `w:fontKey` 比较——头部解混淆，其余直接比较——于是以另一个 key 存储的重复会被认出，而真正不同的字面不会。承载同一款字体的两个字族都会保留：阅读器按字族分别解析，丢掉一个就等于丢掉那个字族的嵌入。没有独立粗体文件时 Word 会合成粗体，因此渲染结果不变。

这一遍只作用在转换写出的 `.docx` 上：`odt` 每个字族只有一个部件，没有可重复的东西。

## 测试

`tests/content.spec.ts` 覆盖每一种收尾标点、换行切分，以及不带正文的标题。`tests/fonts.spec.ts` 覆盖从一个集合读出多个字族、受许可限制的孪生字面、表数据越出文件的字面、重建时对绝对偏移的改写，以及四个中文族名转义后必须互不重复的条目名，夹具是 `tests/font-fixtures.ts` 里的合成集合。`tests/docx-fonts.spec.ts` 覆盖两把混淆 key、同长度与不同长度的非重复、仍被留存关系点名的部件、无法解析的 key，以及没有字体表的包。`tests/metrics.spec.ts` 钉住五个族名，`tests/odf.spec.ts` 钉住经由它们解析的样式，`tests/tool.spec.ts` 在真实转换 seam 上驱动整次调用。

用户自己的那次调用在改后的代码上、对真实字体与本机 LibreOffice 重放：`.docx` 从 15.1 MB 降到 8.5 MB，`一、压实工作责任：` 是 `Level1Heading` 文本段、其后正文为仿宋，紧接的第二层条目同样正确切分。五款字体齐备时，`.odt` 携带五个互不重名的 `Fonts/*.ttf` 部件，导出声明 `仿宋_GB2312`、`楷体_GB2312`、`黑体`、`方正小标宋简体`、`宋体`，每个字族各一条 `w:embedRegular`；把这份 `.docx` 与 `.odt` 交给 LibreOffice 渲染，用到的正是这五款字面、没有替身。WPS 那一环由用户验收，不是本仓库能测的：同一份被 WPS 替换过字体的文档，在只改写族名、其余一字未动之后，渲染即正确。

## 备选方案

**继续只按「。」切分，并要求模型用「。」收尾标题。** 规则是可查的、README 也写明了，所以缺陷可以归给模型。但它不该由模型来补：工具导出的是一个排版归自己所有的元素，而写出「标题：正文」的模型写的是对的公文。不闭合的标题在真实公文里就是常规形式，而这条限制恰恰落在它身上。

**按上一注提出并否决的「任意句末标点」切分。** 上一注给出的风险是：正文里较早出现的同类标点也会被切开。把集合限定在标题可以收尾的标点上——`。！？；：`，不含逗号——就把这一风险收缩到 `一、什么是"一网通办"？正文` 这类本身读法就含混的写法，同时消除了真实报告的那处失败。正是上一注留下了那条备选的记录，才使这次反转成为一项决定而不是疏忽。

**把「：」从边界集合里拿掉。** 它正是被报告段落所使用的标点，而用冒号引出正文的标题很常见；拿掉它等于把缺陷留在原地。

**只读 `.ttf`，要求部署方自行抽取宋体。** SimSun 在每一台 Windows 机器上、以及在桌面端自己的字体暂存目录里都以集合形式存在。必须先把字体转换一遍工具才能携带，运维不会去做；而工具也无法区分一个「不存在」的字族与一个「用不了」的字族。

**保留英文族名，声明 WPS 不受支持。** 这份文件按其他任何标准衡量都是正确的，所以缺陷可以留给 WPS。但它不该由 WPS 来补：字体文件两个名字都认，标准本身用中文称呼这些字面，而写着 `SimHei` 的文档在发生替换时还会让读者误以为版面要的是另一款字体。

**把两个名字都写进文档。** 一个段落每种文字只有一组 `w:rFonts`，而不是候选清单；一个 `<w:font>` 要挂两个名字，就得为同一个文件嵌两份部件才能自洽。只用一个文件与阅读器都认的名字，把这个问题直接消掉。

**像条目名助手最初那样，把每个非 ASCII 字符都换成一个裸下划线。** 它差一点就发出去了，而且是静默破坏性的：标准那五款字族里有两对会撞名，包里留下的是后写入的那款。转义成码点是单射，条目仍是 ASCII，而本来就是 ASCII 的字族条目一字不变。

**用 `fontkit` 之类的字体库解析集合。** 理由与上一注拒绝用它读 `name` 表相同：格式是公开且稳定的，读取器只需要头、一个目录、一张表和一次重建，而该库会为这些之外的东西引入字形轮廓、整形与第三方声明条目。重建约六十行，其正确性由 LibreOffice 自己写出的文件来断言。

**逐字节比较存储的部件。** 第一版实现就是这么做的，结果静默地什么都没删：两个槽存的字节本就不同。比较必须透过 key；测试夹具先断言原始字节不同，再断言重复被找到。

**无条件丢掉 bold 槽，而不比较字体。** 真正带独立粗体字面的字族会因此丢字。同一个文件里 LibreOffice 为 Liberation Serif 与 Liberation Sans 写出了四份真正不同的部件，它们能通过这一遍，正是因为比较保留了它们。

## 后果

首个标点是逗号、且其后接有正文的标题仍会整段留在层次字体里；README 说明了这一点。读取集合要为每个被携带的字面付一次重建成——在 apply 时付一次。`.docx` 这一遍会读取并重写转换后的包——对刚写出的文件多走一遍——并报告文件实际具有的大小。黑体与宋体仍须由部署方提供；本篇移除的是携带它们的代码障碍，不是许可障碍，结果备注仍然点名哪些字面随行、哪些没有。

这些中文族名现在是工具写出的唯一名字，因此只按英文名解析字体的阅读器会去替换。报告问题的机器上没有 Word 可供反向验证；涉及其中的每个文件两个名字都认，Windows 验收清单里带着这一项检查。转义后的条目名改变了 ODT 包对非 ASCII 字族的呈现——是 `Fonts/_u4EFF_u5B8B_GB2312.ttf` 而不是带着汉字的文件名——这只对查看包内部的人有影响。
